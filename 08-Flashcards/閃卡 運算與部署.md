## 🚀 Cloud Run

Cloud Run 的三層資源模型是什麼？::Service（穩定 URL）→ Revision（不可變快照）→ Instance（執行容器的實體）

為什麼 Cloud Run 的回滾可以是秒級？::因為 revision 不可變，回滾只是把流量指回舊 revision，不需重新建置或部署

Cloud Run 每個實例的預設並行請求數？::80

Cloud Run 並行的上限？::1000

什麼時候該把 Cloud Run 的 concurrency 設為 1？::程式非執行緒安全、CPU 密集、或每個請求需要大量記憶體

Cloud Run 的請求逾時預設與上限？::預設 5 分鐘（300 秒），上限 60 分鐘（3600 秒）

Cloud Run 實例數的估算公式？::實例數 ≈ 進行中的請求數 ÷ concurrency

Cloud Run 的記憶體與 vCPU 上限？::32 GiB 記憶體、8 vCPU

Cloud Run 容器契約的四個要求？::監聽 $PORT、綁定 0.0.0.0、無狀態、處理 SIGTERM 優雅關閉

如何消除 Cloud Run 的冷啟動？::設定 --min-instances（並可搭配 startup CPU boost），代價是持續計費

Cloud Run 的兩種 CPU 配置模式差在哪？::cpu-throttling（預設，只在請求期間有 CPU，最省）vs no-cpu-throttling（always allocated，背景工作/連線池需要）

回應送出後還要做背景工作，Cloud Run 上有哪兩個正解？::① 把工作丟給 Cloud Tasks（首選）② 設 --no-cpu-throttling

如何在生產環境測試新版本而完全不影響使用者？::gcloud run deploy --no-traffic --tag candidate，然後用 tag 專屬 URL 測試

Cloud Run 上做 10% canary 的指令？::gcloud run services update-traffic SVC --to-tags candidate=10

Cloud Run 立即回滾的指令？::gcloud run services update-traffic SVC --to-revisions OLD_REV=100

Cloud Run 不指定 --service-account 會用什麼身分？::default compute service account（權限過大，考試中是錯的）

`gcloud run deploy --source .` 背後用了什麼？::Cloud Build + Buildpacks（不需要 Dockerfile），映像推到 Artifact Registry

Cloud Run 保護資料庫連線數的設定是什麼？::--max-instances 搭配小的連線池

Cloud Run 的 /tmp 有什麼特性？::它在記憶體裡，會算進記憶體用量，且實例消失就沒了

Cloud Run 支援 sidecar 嗎？DaemonSet 呢？::支援多容器（sidecar）；不支援 DaemonSet（沒有節點概念）

## 📦 Cloud Run Jobs / functions

Cloud Run Jobs 的三層模型？::Job（定義）→ Execution（一次執行）→ Task（平行單位）

Jobs 裡用來切分工作的兩個環境變數？::CLOUD_RUN_TASK_INDEX（第幾號，0-based）與 CLOUD_RUN_TASK_COUNT（總數）

Cloud Run Jobs 的 --parallelism 作用？::限制同時執行的 task 數，用來保護下游

什麼情況該用 Cloud Run Jobs 而不是 Service？::沒有 HTTP 端點需求、跑完就結束、可能超過 60 分鐘、需要平行切分資料

事件驅動的 Cloud Run function 失敗後預設會重試嗎？::不會，要開 --retry；但開了要小心毒藥訊息無限重試（需 DLQ + 冪等）

## ☸️ GKE

GKE Autopilot 與 Standard 的計費差異？::Autopilot 按 Pod requests 計費；Standard 按節點計費

列出三個必須用 GKE Standard 的需求::特權 DaemonSet（節點層級 agent）、SSH 進節點、自訂核心模組/GPU 驅動、hostNetwork

Kubernetes 三種 probe 的失敗後果？::startupProbe 失敗→重啟容器；readinessProbe 失敗→從 Service endpoints 移除（不重啟）；livenessProbe 失敗→重啟容器

startupProbe 最重要的特性？::在它成功之前，readiness 與 liveness 都不會執行 → 專治啟動慢的應用

livenessProbe 絕對不該做什麼？::檢查下游依賴 —— 否則下游故障會造成全部 Pod 連鎖重啟

probe 的最長容忍啟動時間公式？::initialDelaySeconds + failureThreshold × periodSeconds

probe 的 timeoutSeconds 預設值是多少？為什麼危險？::1 秒；GC 暫停或瞬間高載就會誤判為失敗

requests 與 limits 的意義？::requests 是保證配額（排程依據）；limits 是上限

CPU 超過 limit 與記憶體超過 limit 的行為差異？::CPU 被節流（變慢）；記憶體直接被殺（OOMKilled）

Kubernetes 的三個 QoS 等級與驅逐順序？::Guaranteed（requests==limits，最後被驅逐）> Burstable > BestEffort（最先被驅逐）

HPA 用 CPU 百分比的前置條件？::容器必須設定 resources.requests.cpu

HPA 依 Pub/Sub 積壓擴充需要什麼？::External metric（pubsub.googleapis.com|subscription|num_undelivered_messages）+ Custom Metrics Stackdriver Adapter

HPA 與 Cluster Autoscaler 的關係？::HPA 加 Pod → 節點不夠 → CA 加節點（接力，不是競爭）

VPA 與 HPA 可以同時用嗎？::不要對同一個指標（如 CPU）同時用；VPA 調記憶體 + HPA 調 CPU 可接受

PodDisruptionBudget 的作用與常見誤設？::保證自願性中斷時至少 N 個 Pod 可用；誤設 minAvailable = replicas 會讓節點永遠無法排空

kubectl get endpoints 是空的代表什麼？::沒有「符合 selector 且 Ready」的 Pod → selector 錯或 readiness 沒通過

CrashLoopBackOff 第一個該執行的指令？::kubectl logs POD --previous（看上次崩潰的 log）

ImagePullBackOff 最常見的權限原因？::節點/服務的 SA 缺 roles/artifactregistry.reader

滾動更新期間出現 502 的正解？::preStop hook（sleep）+ 應用處理 SIGTERM + 足夠的 terminationGracePeriodSeconds

Workload Identity for GKE 的四個設定步驟？::① 叢集啟用 workload-pool ② 建 GSA 並授權 ③ KSA 綁 GSA（roles/iam.workloadIdentityUser）④ 註解 KSA

GCP IAM 與 Kubernetes RBAC 的分工？::IAM 決定能否呼叫叢集 API；RBAC 決定叢集內能對哪些物件做什麼

「限制某團隊只能操作某 namespace」該改哪一層？::Kubernetes RBAC（不是 IAM）

StatefulSet 與 Deployment 的關鍵差異？::StatefulSet 有穩定的名稱與持久磁碟、有序啟動終止（適合資料庫/Kafka）

Ingress 與 Gateway API 何時選哪個？::簡單 host/path 路由用 Ingress；需要權重分流、header 路由、多團隊共用 LB 用 Gateway API

## 🎭 部署策略

五種部署策略？::Recreate、Rolling update、Blue/Green、Canary、A/B testing

Canary 與 A/B testing 的目的差異？::Canary 找技術問題（錯誤率/延遲，依比例分流）；A/B 比較業務成效（轉換率，依使用者屬性分流）

Blue/Green 的優點與代價？::回滾瞬間完成、可完整測試；代價是需要雙倍資源

所有漸進式發布的共同前置條件？::新舊版本必須能同時存在 → API、資料庫 schema、訊息格式都要向後相容

資料庫欄位要改名的安全三階段？::expand（先加新欄位並雙寫）→ migrate（遷移資料）→ contract（所有舊版下線後才刪舊欄位）

回滾的三個層次？哪一層最難？::流量層（秒）、工作負載層（分鐘）、**資料層（最難）**

Cloud Build 與 Cloud Deploy 的分工？::Cloud Build = CI（建置測試產生產出物）；Cloud Deploy = CD（把同一個產出物晉升過 dev→staging→prod）

什麼關鍵詞指向 Cloud Deploy？::promote the same artifact through environments、approval before production、managed canary with rollback

## 🖥 Compute Engine / App Engine

MIG 提供哪三個能力？::自動擴充、自動修復（autohealing）、滾動更新

Local SSD 與 Persistent Disk 的關鍵差異？::Local SSD 超低延遲但 VM 停止就消失；PD 是持久的網路磁碟

什麼是 Strangler Fig 模式？::在單體前放一層路由（LB/API Gateway），新功能導向新服務、舊功能留單體，逐步替換

App Engine Standard 與 Flexible 哪個能縮到 0？::Standard 可以；Flexible 不能（最少 1 個實例）

全新專案該選 App Engine 還是 Cloud Run？::Cloud Run
