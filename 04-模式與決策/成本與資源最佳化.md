# 成本與資源最佳化

> [!abstract] 一句話定位
> 官方考點原文：**「定義工作負載的資源需求」** 與 **「最佳化成本與資源使用」**。
> 考試不會問價格數字，而是問**「哪個選項在滿足需求的前提下最便宜」** — 也就是選型判準。

---

## 📏 先定義資源需求（官方考點）

```mermaid
flowchart LR
    M["① 量測<br/>(現況的 CPU/記憶體/延遲/QPS)"] --> E["② 估算<br/>(單位請求成本 × 預期流量)"]
    E --> S["③ 設定<br/>(requests/limits、concurrency、min/max)"]
    S --> O["④ 觀察<br/>(飽和度、節流、OOM、延遲)"]
    O --> A["⑤ 調整"]
    A --> O
```

| 平台 | 要設什麼 | 怎麼決定 |
|---|---|---|
| **Cloud Run** | `--cpu`、`--memory`、`--concurrency`、`--min-instances`、`--max-instances` | 壓測找「單一實例在目標延遲下能扛的併發」→ 設 concurrency；記憶體看實際用量 + 緩衝 |
| **GKE** | `resources.requests` / `limits` | 用 **VPA `Off` 模式**看建議值；或看歷史 p95 用量 |
| **Compute Engine** | 機型家族與大小 | 用 **Recommender** 的機型建議 |

> [!important] requests / limits 的判準
> - **`requests` = 穩定狀態下的 p95 用量**（排程依據，設太低會被驅逐、HPA 失效）
> - **`limits` = 尖峰可容忍的上限**（記憶體超過會 **OOMKilled**，CPU 超過只是被節流）
> - 關鍵服務 → `requests == limits`（**Guaranteed** QoS，最後才被驅逐）
> 見 [[GKE 工作負載 健康檢查與自動擴充]]。

## 💰 各服務的省錢槓桿

### 運算
| 槓桿 | 說明 | 注意 |
|---|---|---|
| **縮到 0**（Cloud Run） | 沒流量不計費 | 代價是冷啟動 |
| **提高 concurrency**（Cloud Run） | 同樣流量用更少實例 | 記憶體/CPU 要夠，程式要執行緒安全 |
| **min-instances 設 0** | 省錢 | 有冷啟動；有 SLA 要求時要權衡 |
| **Spot VM / GKE Spot 節點** | 大幅折扣 | 隨時被回收 → 只給可中斷工作 |
| **Autopilot** | 只付 Pod requests | 節點閒置不用你付 |
| **Committed Use Discount (CUD)** | 承諾 1/3 年換折扣 | 穩定基載才適合 |
| **右尺寸化（rightsizing）** | 用 Recommender / VPA 建議調整 | 最容易被忽略的大省錢點 |
| **關掉非生產環境** | 用 Cloud Scheduler 下班關、上班開 | dev/test 環境 |

### 儲存
| 槓桿 | 說明 |
|---|---|
| **Storage class + lifecycle** | 30 天後 Nearline、365 天後 Archive、7 年後刪 → 見 [[Cloud Storage]] |
| **Autoclass** | 存取模式不明時自動搬移 |
| **清理未標記映像** | Artifact Registry 的 **cleanup policy** |
| **清理舊物件版本** | lifecycle `numNewerVersions` |
| **選對 region** | 跨區流量費用可觀；運算與資料同區 |
| **PD 快照策略** | 別無限保留 |

### 資料庫
| 槓桿 | 說明 |
|---|---|
| 機型右尺寸化 + 自動儲存擴充 | Cloud SQL |
| **read replica 只在需要時開** | 每個 replica 都要錢 |
| **Bigtable autoscaling** | 依 CPU 自動調節點數 |
| **BigQuery：分區 + 叢集 + 不要 `SELECT *`** | 最大的省錢點 → 見 [[BigQuery 給開發者]] |
| **BigQuery slot 預留** | 穩定用量比 on-demand 便宜 |
| **Firestore：減少索引** | 索引會增加寫入成本 |
| **快取降低資料庫負載** | [[Memorystore 與快取策略]] |

### 網路與可觀測性
| 槓桿 | 說明 |
|---|---|
| **Cloud CDN** | 減少來源流量與運算 |
| **同區部署** | 避免跨區/跨洲流量費 |
| **Logging exclusion** | 排除健康檢查與 DEBUG log（**常常是最大的意外帳單**） |
| **縮短 log 保留期 / 歸檔到 GCS** | 見 [[Cloud Logging]] |
| **控制指標基數** | 高基數 label = 大量時間序列 = 高費用 → 見 [[Cloud Monitoring 與 SLO]] |
| **Trace 取樣** | 不要 100% |

## 🧮 Cloud Run 成本心智模型

```
成本 ≈ (實例數 × 存活時間) × (CPU 單價 × vCPU + 記憶體單價 × GiB) + 請求數費用
實例數 ≈ 進行中的請求數 ÷ concurrency
```

| 想降低成本 | 做法 | 風險 |
|---|---|---|
| 減少實例數 | **提高 concurrency** | 記憶體壓力、延遲上升 |
| 減少實例存活時間 | `min-instances=0` | 冷啟動 |
| 減少單位成本 | 降低 `--cpu` / `--memory` | 延遲上升、OOM |
| 減少 CPU 計費時間 | 用預設 `cpu-throttling`（只在請求期間計 CPU） | 背景工作會被凍結 |
| 減少請求數 | 快取、CDN、批次 | 資料新鮮度 |

> [!warning] 最常見的浪費
> 1. `min-instances` 設在**所有環境**（dev/staging 也保持暖機）。
> 2. `concurrency=1`（誤以為比較安全）→ 實例數 80 倍。
> 3. 記憶體設 4 GiB 但只用 300 MiB。
> 4. `--no-cpu-throttling` 但其實沒有背景工作。

## 🎯 考點速記

| 看到題目說… | 就想到 |
|---|---|
| `most cost-effective` + 間歇性流量 | **Cloud Run**（縮到 0） |
| `pay only for what pods request` | **GKE Autopilot** |
| `fault-tolerant batch, minimize cost` | **Spot VM / Spot 節點池** |
| `steady baseline load for 3 years` | **Committed Use Discount** |
| `data accessed once a year` | **Archive** class + lifecycle |
| `unknown access patterns` | **Autoclass** |
| `reduce BigQuery cost` | 分區 + 叢集 + 不要 `SELECT *` + max bytes billed |
| `logging bill is too high` | **Exclusion** + 縮短保留 + 歸檔到 GCS |
| `monitoring cost rising` | **指標基數**過高 |
| `right-size our VMs / pods` | **Recommender / VPA** |
| `avoid cross-region egress charges` | 運算與資料**同區** |
| `serve static content cheaply at scale` | **Cloud CDN** + GCS |
| `prevent runaway costs` | **Budget alert + 配額上限 + max-instances** |

## 💣 真實場景陷阱

1. **為了省錢把 `requests` 設太低**：Pod 被驅逐、HPA 失效、延遲爆炸 → 反而更貴（事故成本）。
2. **cross-region 流量**：bucket 在 `us`、運算在 `asia-east1` → 看不見的持續費用。
3. **忘記刪練習資源**：Cloud SQL 執行個體、GKE 叢集、Memorystore、NAT 都是**持續計費**（即使沒用）。
4. **log 沒有 exclusion**：健康檢查 log 佔 90%。
5. **Bigtable / Spanner 最小容量**：小專案的固定成本吃掉預算。
6. **只看單價不看架構**：把運算搬到便宜區域但資料在別區 → 流量費超過省下的錢。
