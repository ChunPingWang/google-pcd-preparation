## 📝 Cloud Logging

在 Cloud Run / GKE 上怎麼做結構化記錄？::把 JSON 寫到 stdout，Logging 會自動解析成 jsonPayload

結構化 log 的三個最重要特殊欄位？::severity、message、**logging.googleapis.com/trace**

為什麼要結構化 log？::可以用欄位精準查詢（如 jsonPayload.order_id）、做 log-based metric、關聯 trace

多行 stack trace 直接 print 會有什麼問題？::被拆成多筆 log → Error Reporting 無法聚合。要放在單一欄位

Log Router 的四種目的地？::Logging bucket、Cloud Storage（歸檔）、BigQuery（SQL 分析）、Pub/Sub（串到外部 SIEM）

建立 sink 後最容易漏掉什麼？::給 sink 的 **writer identity** 目的地的 IAM 權限（漏了會靜默失敗）

`_Default` 與 `_Required` log bucket 的保留期？::_Default 30 天（可改 1-3650）；_Required 400 天（不可改、免費）

降低 Logging 費用的主要手段？::Exclusion（排除健康檢查/DEBUG）+ 縮短保留期 + 歸檔到 GCS

「已經有 log，想設警示且不改程式」→ 用什麼？::log-based metric（+ alerting policy）

log-based metric 與 OTel 自訂指標的取捨？::已有 log 不想改程式 → log-based；需要精確計數/低延遲/業務數值 → 自訂指標

log-based metric 的 label 要注意什麼？::不要用高基數值（user ID）→ 指標數量與費用爆炸

Admin Activity 與 Data Access audit log 的差別？::Admin Activity 永遠開啟且免費；**Data Access 預設關閉**（BigQuery 除外）、會計費

「稽核誰讀取了 GCS 物件」要先做什麼？::啟用 Data Access audit log

工作負載沒有 log 最可能的原因？::SA 缺 roles/logging.logWriter

## 📊 Cloud Monitoring 與 SLO

四個黃金訊號？::延遲（Latency）、流量（Traffic）、錯誤（Errors）、飽和度（Saturation）

為什麼不該只警示 CPU？::CPU 是原因不是症狀；要警示面向使用者的症狀（延遲、錯誤率）

「平均延遲正常但使用者抱怨慢」→ 該看什麼？::p95 / p99 百分位

SLI / SLO / SLA / error budget 的定義？::SLI=量測值；SLO=目標+時間窗；SLA=對外合約（通常較寬鬆）；error budget = 1 - SLO

99.9% / 30 天 的 error budget 約多少時間？::約 43 分鐘

error budget 的管理意義？::把「可靠性 vs 發布速度」量化成可協商的數字（預算用完就凍結發布）

為什麼 burn-rate 警示比固定門檻好？::它衡量「對月度預算的實際影響」，短暫抖動不觸發 → 大幅減少假警報

多視窗 burn-rate 的兩個常用設定？::快速燒（1 小時 > 14.4x 且 5 分鐘也超過 → page）；慢速燒（6 小時 > 6x → 開 ticket）

自訂指標的三種送法？官方推薦？::OpenTelemetry（推薦）、Monitoring API、Managed Service for Prometheus

為什麼不能用 user ID 當 metric label？該放哪？::高基數 → 時間序列爆炸、費用飆升；高基數資訊放 log 或 trace span 屬性

Uptime check 與 readinessProbe 的差別？::uptime check 是從外部多位置的黑箱監控（使用者視角）；probe 是叢集內部的健康判斷

要讓警示自動觸發修復動作，通知管道選什麼？::Pub/Sub（再接 Cloud Run/Functions）

警示應該附上什麼？::runbook 文件連結（documentation 欄位）

送自訂指標需要什麼角色？::roles/monitoring.metricWriter

## 🔬 Trace / Profiler / Error Reporting

三個工具各回答什麼問題？::Trace=「時間花在哪個服務」；Profiler=「哪一行程式碼在燒資源」；Error Reporting=「哪個例外最頻繁」

從「使用者說很慢」到定位到程式碼的工具順序？::Monitoring（範圍）→ Trace（哪一段）→ Logging（為什麼，用 trace ID）→ Profiler（哪一行）

trace context 傳播的兩種 header？::traceparent（W3C，OTel 預設）與 X-Cloud-Trace-Context（Google 傳統格式）

trace 關聯的三個必要條件？::① 呼叫下游時注入 header ② 收到請求時繼承 context ③ **每筆 log 寫入 logging.googleapis.com/trace**

只做傳播但 log 沒帶 trace ID 會少什麼能力？::無法從 Trace 一鍵跳到對應的 log（也無法用 trace= 撈全鏈 log）

怎麼讓 trace 跨過 Pub/Sub？::把 trace context 放進**訊息屬性**，消費端 extract 後續接

Cloud Profiler 為什麼可以在生產環境長期開著？::它是低開銷的持續性剖析

「懷疑生產環境記憶體洩漏」用什麼？::Cloud Profiler 的 heap 剖析

Error Reporting 收不到例外的四個原因？::severity 不是 ERROR 以上、stack trace 被拆成多筆、例外被吞掉（except: pass）、格式不像 stack trace

為什麼要設定 service_version？::才能知道是哪個版本引入問題，也能比較最佳化前後的 profile

高基數資訊（order ID）該放 span 屬性還是 metric label？::span 屬性（metric label 會爆）

## 🔭 OpenTelemetry

OTel 的三種訊號？::traces、metrics、logs

為什麼要用 OTel Collector？（四個價值）::解耦後端、處理（取樣/過濾/去 PII）、批次與重試、集中設定

Head-based 與 tail-based 取樣的差別？::head 在請求開始時決定（簡單便宜）；tail 等 trace 完成後決定（可保留錯誤與慢的 trace）

實務上的取樣建議？::正常流量低取樣 + 錯誤/高延遲全取樣（tail-based）

為什麼要用 BatchSpanProcessor？::避免每個 span 同步送出造成延遲暴增

自動與手動 instrumentation 的分工？::自動涵蓋框架與用戶端（80%）；手動 span 只加在業務上有意義的區段

在 Cloud Run 上怎麼跑 OTel Collector？::作為 **sidecar 容器**（Cloud Run 支援多容器）

## 🚚 Cloud Build / Artifact Registry

Cloud Build 的每個 step 本質是什麼？::一個容器（name 就是映像）

step 之間怎麼共用資料？::透過 `/workspace` 目錄（**環境變數不會跨 step**）

Cloud Build 預設是循序還是平行？怎麼平行？::預設循序；設 `waitFor: ['-']` 表示不等任何步驟 → 立即開始

加速 Cloud Build 的四種方法？::平行化 step、快取（--cache-from / kaniko cache）、更大的 machineType、精簡 Dockerfile

在 Cloud Build 安全使用祕密的方式？::availableSecrets（Secret Manager）+ secretEnv；**不要**放 substitutions

Cloud Build 什麼時候需要 private worker pool？::要存取私有資源（私有 GKE、地端 DB）或需要固定出口 IP

Cloud Build 的 provenance 是什麼用途？::產生可驗證的建置來源紀錄（SLSA），供 Binary Authorization 判斷

映像 tag 的最佳實務？::用 $SHORT_SHA 或 digest，不要只用 :latest（可追溯、可回滾、Binary Auth 需要 digest）

生產部署需要人工核准怎麼做？::Cloud Build 觸發器的 --require-approval，或 Cloud Deploy target 的 requireApproval

Artifact Registry 的三種 repository mode？::Standard（自己推）、Remote（代理快取外部如 Docker Hub）、Virtual（聚合多個 repo 成單一端點）

「避免 Docker Hub rate limit」用什麼？::Remote repository（代理 + 快取）

Artifact Registry cleanup policy 的作用？::自動刪除舊/未標記的映像版本（省錢並減少未修補的殘留）

GKE ImagePullBackOff 的權限原因？::節點的 SA 缺 roles/artifactregistry.reader（跨專案時要額外授權）

Container Registry 與 Artifact Registry 的關係？::Artifact Registry 取代了 Container Registry（gcr.io）→ 考試選 Artifact Registry

## 🧪 開發環境與 AI 工具

哪些 Google Cloud 服務有官方 emulator？::Firestore、Datastore、Pub/Sub、Bigtable、Spanner

哪兩個重要服務**沒有**官方 emulator？::Cloud Storage 與 BigQuery（用測試 bucket/dataset 或第三方 fake）

設定 emulator 後程式碼要改嗎？::不用 —— 設 `*_EMULATOR_HOST` 環境變數後用戶端程式庫會自動改連且不需憑證

Cloud Shell 與 Cloud Workstations 的差別？::Cloud Shell 是瀏覽器內的臨時環境（只有 $HOME 持久、規格固定）；Workstations 是代管、可自訂、在你的 VPC 內的持久開發環境

「程式碼不得存在開發者筆電」+「要連私有資源」→ 選什麼？::Cloud Workstations

Cloud Code 能做什麼？::在 IDE 內部署/除錯 Cloud Run 與 GKE、本機開發迴圈（Skaffold）、YAML 驗證

Gemini Code Assist 與 Gemini Cloud Assist 的差別？::Code Assist 在 IDE 內輔助寫程式與**產生單元測試**；Cloud Assist 輔助雲端維運排查（解釋 log、產生查詢、推測根因）

用 AI 產生單元測試時的三個把關點？::讓它先讀懂既有測試風格、重點放邊界與錯誤路徑、**產出必須人工審查**（避免 assert 過寬）

MCP server 在 AI 開發中的角色？::讓 AI 助理安全地取得外部上下文與工具（你的 API/資料庫/文件）

emulator 測試通過但上雲失敗的三個常見原因？::emulator 不驗證 IAM、索引行為不同、配額與延遲不同

## 🤖 Gen AI（2026 新考點）

生產環境該用 Vertex AI 還是 Gemini Developer API？為什麼？::Vertex AI —— 用 IAM/ADC 驗證，支援 VPC-SC、CMEK、資料落地與稽核

如何確保模型輸出能被程式可靠解析？::結構化輸出（response_mime_type=application/json + JSON schema）

Function calling 的權限檢查該在哪裡做？::在**你的程式碼**裡 —— 模型輸出是「請求」不是「授權」（防 prompt injection）

「回答必須基於公司文件」該用什麼？為什麼不是 fine-tuning？::RAG / grounding；多數「答案不對」是上下文不足，不是模型能力問題

把 Gen AI 整合進服務必要的五個韌性機制？::timeout、重試（退避）、斷路器、快取、降級（fallback）+ 監控

控制 Gen AI 成本的四個做法？::選小模型處理簡單任務、精簡 prompt 與限制 max_output_tokens、快取（含 context caching）、批次預測

Cloud Run 上跑串流 LLM 回應要注意什麼？::請求逾時（預設 5 分鐘，最長 60 分鐘）與記憶體/並行設定

AI 功能該監控哪些指標？::token 用量、延遲、錯誤率、被安全設定過濾的比率
