## 🧭 五個服務的定位

Cloud Scheduler 一句話定位？::到時間就去戳一下（全代管 cron）

Eventarc 一句話定位？::GCP 資源變化 → 轉成 CloudEvents 標準事件送出

Pub/Sub 一句話定位？::這件事發生了，誰想知道自己來訂（扇出、解耦、串流）

Cloud Tasks 一句話定位？::這件工作稍後做，而且要控速（對單一目標派工）

Workflows 一句話定位？::照這個流程一步步做，我幫你記狀態（編排）

「多個服務要各自處理每一則訊息」→ 怎麼做？::一個 topic、多個 subscription（不是一個 subscription 多個 consumer）

「呼叫第三方 API 每秒最多 10 次」→ 選什麼？::Cloud Tasks（佇列的 max-dispatches-per-second）

「30 分鐘後檢查訂單是否付款」→ 選什麼？::Cloud Tasks 的 scheduleTime

「檔案上傳到 GCS 後自動處理」→ 選什麼？::Eventarc 觸發器 → Cloud Run

「有人修改 IAM 政策要通知」→ 選什麼？::Eventarc 的 Cloud Audit Logs 觸發器（需啟用對應 audit log）

「多步驟流程、有條件分支、要等人工核准、失敗要補償」→ 選什麼？::Workflows

「每天凌晨 2 點跑 3 小時的批次」→ 完整組合？::Cloud Scheduler → Cloud Run Jobs（不要讓 Scheduler 同步等）

編排（orchestration）與協作（choreography）的差別？::編排有中央大腦與狀態（Workflows）；協作各服務靠事件自行反應（Pub/Sub），耦合最鬆但難追蹤全局

## 📨 Pub/Sub

Pub/Sub 的傳遞保證？::at-least-once（可選 exactly-once delivery）

Pub/Sub 的 ack deadline 預設與上限？::預設 10 秒，上限 600 秒（10 分鐘）

Pub/Sub 訂閱未 ack 訊息的保留期預設？::7 天（可設 10 分鐘 ～ 7 天）

Pub/Sub topic 層的訊息保留上限？::31 天（用於 replay）

Pub/Sub 訊息大小上限？::10 MB

超過 10 MB 的 payload 怎麼處理？::claim-check 模式 —— 存到 Cloud Storage，訊息只帶路徑

ordering key 的保證範圍與兩個代價？::只保證同一個 key 內有序；代價是單 key 吞吐約 1 MB/s、一則失敗會阻塞同 key 後續訊息

subscription filter 依什麼過濾？有什麼限制？::依訊息屬性（不能看 payload）；建立後不能修改

要重播昨天的事件有哪兩種機制？::topic retention + seek，或 snapshot（需事先設定）

dead-letter topic 解決什麼問題？沒有它會怎樣？::毒藥訊息；沒有它會無限重試、塞住訂閱且燒錢

DLQ 建好之後還要做什麼？::對 DLQ 的訊息數/積壓設警示（不然問題只是被藏起來）

啟用 exactly-once delivery 後還需要冪等嗎？為什麼？::需要。若處理完成但 ack 前程序崩潰，重啟後仍會再處理一次

「訊息一直被重複處理且 worker CPU 滿載」的原因與解法？::處理時間超過 ack deadline → 降低 flow control 的 max_messages 或延長 ack deadline

Pub/Sub push 訂閱如何安全呼叫需驗證的 Cloud Run？::建立 push 訂閱時指定 --push-auth-service-account，該 SA 需有 run.invoker

把事件寫進 BigQuery 最省程式碼的方式？::Pub/Sub 的 BigQuery 訂閱

依 Pub/Sub 積壓自動擴充 GKE 工作者需要什麼？::HPA External metric（num_undelivered_messages）+ Custom Metrics Adapter

## 📬 Cloud Tasks

Cloud Tasks 與 Pub/Sub 的四個決定性差異？::① 一對一派工 vs 一對多扇出 ② 佇列層級速率控制 vs 無 ③ 可排程單一任務 vs 不可 ④ 有 task name 去重 vs 無

Cloud Tasks 有 DLQ 嗎？::沒有。重試用盡即丟 → 要自行記錄失敗

Cloud Tasks 的排程上限？::約 30 天

Cloud Tasks 保護脆弱下游的兩個設定？::max-dispatches-per-second 與 max-concurrent-dispatches

Cloud Tasks 呼叫需驗證的 Cloud Run 要怎麼設？::任務帶 oidc_token（指定 SA + audience），該 SA 需有 run.invoker；建立者需對該 SA 有 actAs

dispatch_deadline 設太短會發生什麼？::Cloud Tasks 判定失敗並重試 → 同一個工作被重複執行

## 🔌 Eventarc

Eventarc 的三種事件來源？::直接事件（GCS/Firestore 等原生事件）、Cloud Audit Logs、Pub/Sub 訊息

Eventarc 底層用什麼傳輸？帶來什麼設計義務？::Pub/Sub → at-least-once → 處理器必須冪等

Eventarc 處理器回 500 會發生什麼？永久錯誤該回什麼？::會重送；永久性錯誤應回 2xx 並自行記錄/送 DLQ，否則無限重試

GCS → Cloud Run 的 Eventarc 觸發器需要哪些 IAM？::觸發器 SA 需 run.invoker + eventarc.eventReceiver；GCS 服務代理需 pubsub.publisher；建立者需 actAs

處理 GCS 事件時把結果寫回同一個 bucket 會發生什麼？::無限迴圈（自己觸發自己）→ 輸出到不同 bucket 或用 prefix 過濾

Eventarc 與 Pub/Sub 何時選哪個？::事件由 GCP 服務產生 → Eventarc；事件由你自己 publish → Pub/Sub

## 🔀 Workflows / Scheduler

Workflows 的四個關鍵能力？::try/retry/except 錯誤處理、switch/for/parallel 控制流、callback（等外部/人工）、連接器（呼叫 GCP 服務）

Workflows 呼叫 Cloud Run 用哪種 auth？呼叫 Google Cloud API 呢？::Cloud Run 用 OIDC；Google Cloud API 用 OAuth2

Workflows 為什麼適合「等待外部系統」？::按步驟計費，等待期間很便宜（比在 Cloud Run 裡 sleep 省得多）

Workflows 怎麼實作 Saga？::在 except 區塊執行補償步驟（補償本身也要冪等）

Cloud Scheduler 忘記設什麼最容易出錯？::--time-zone（預設 UTC，夏令時間會出問題）

Cloud Scheduler 的傳遞保證？::at-least-once → 處理器要冪等

## 🛡 韌性模式

為什麼 at-least-once 一定要冪等？::重複送達是規格不是 bug；不冪等就會重複扣款/重複寄信

三種實作冪等的方式？::① 冪等鍵 + 唯一性約束（Firestore create() / Redis SETNX / SQL 唯一索引）② 天然冪等的操作設計（條件式更新/UPSERT）③ 樂觀鎖/版本號

冪等鍵最好用什麼？為什麼？::業務鍵（如 orderId + 步驟名）；跨重送、跨系統都一致，比 message ID 更可靠

指數退避的完整公式？::delay = min(base × 2^attempt, cap) + random(0, jitter)

為什麼一定要 jitter？::否則所有失敗的用戶端在同一時刻一起重試 → 重試風暴（thundering herd）

哪些錯誤該重試？::429、500、503、504（需冪等）、409 ABORTED（重試整個交易）

哪些錯誤不該重試？::400 INVALID_ARGUMENT、401、403、404

「每層都重試 3 次」的問題？::放大效應（3 層 = 27 次呼叫）→ 只在最外層或最合適的一層重試

timeout 預算的原則？::外層的 timeout 必須大於內層的（timeout × 重試次數），否則內層的重試白做

斷路器的三個狀態？::CLOSED（正常）→ OPEN（快速失敗，保護下游）→ HALF_OPEN（試探）

在 GKE 上怎麼實作斷路器？::Cloud Service Mesh 的 DestinationRule outlierDetection（或應用內程式庫）

分散式交易在雲端原生的正解？::Saga + 補償 + 冪等（不是 2PC）

背壓（backpressure）在 GCP 上的工具？::Pub/Sub flow control、Cloud Tasks 速率限制、--max-instances

## 🔗 Cloud API 呼叫

呼叫 Google Cloud API 的建議方式與三個理由？::Cloud Client Libraries；內建 ADC 驗證、內建退避重試、自動分頁

Cloud Run 上用戶端該在哪裡建立？::全域（模組層級）建立一次並重用 —— 不要在每個請求裡建立

列出 500 萬個物件該怎麼寫？::用 iterator（自動翻頁），絕不用 list() 一次全抓

`reduce the amount of data returned` 的手段？::field mask / partial response（fields 參數）

批次的好處與代價？::提升吞吐、降低成本；代價是延遲增加，且要處理「部分成功」

Firestore batch 與 Pub/Sub publish 的上限？::Firestore 500 個操作；Pub/Sub 單次 10 MB 或 1000 則

哪三種東西一定要快取？哪一種不用自己管？::祕密、設定/對照表、昂貴查詢結果；**token 由程式庫自動快取**，不要自己管

`403 SERVICE_DISABLED` 怎麼解？::gcloud services enable（不是改 IAM）

常遇到 429 的四個方向解法？::指數退避 + 降低併發（max-instances/Tasks 節流）+ 批次減少呼叫 + 申請提額
