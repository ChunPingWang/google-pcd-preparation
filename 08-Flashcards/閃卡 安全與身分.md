## 🔑 IAM

IAM 的三種角色類型？考試中哪一種幾乎永遠是錯的？::basic（Owner/Editor/Viewer）、predefined、custom；**basic 永遠是錯的**

IAM 政策綁在哪裡？權限怎麼流動？::綁在資源上，權限往資源階層**向下繼承**（Org → Folder → Project → 資源）

繼承來的權限能在子層級移除嗎？::不能，只有 **IAM Deny Policy** 能阻擋

服務帳戶的四種使用方式（安全性排序）？::① 附加到資源（最好）② Workload Identity Federation ③ impersonation ④ 匯出 JSON 金鑰（最差，考試中是錯的）

`roles/iam.serviceAccountUser` 與 `roles/iam.serviceAccountTokenCreator` 的差別？::前者是 actAs（部署時把 SA 指派給資源）；後者是動態取得該 SA 的 token（impersonation、簽 blob）

Cloud Build 部署 Cloud Run 失敗說 actAs denied → 怎麼修？::給 Cloud Build 的 SA 對**執行時 SA** 的 roles/iam.serviceAccountUser

「在專案層級授權」與「在資源層級授權」哪個好？::資源層級（範圍更小）→ 兩個選項都對時選範圍小的

default compute service account 的問題？::傳統上帶有 roles/editor，權限過大 → 每個工作負載要有專屬 SA

「只在上班時間可存取」或「只能存取特定前綴的物件」用什麼？::IAM Condition（條件式存取）

「即使是 Owner 也絕對不能刪除 X」用什麼？::IAM Deny Policy（或 GCS retention lock，視情境）

「禁止任何人建立 SA 金鑰」用什麼？::Organization Policy（constraints/iam.disableServiceAccountKeyCreation）

「防止資料被複製到邊界外的專案」用什麼？::VPC Service Controls

Cloud Run 服務呼叫另一個需驗證的 Cloud Run，要給誰什麼角色？::目標服務上給呼叫方的 SA `roles/run.invoker`

工作負載要寫 log / 指標 / trace 各需要什麼角色？::roles/logging.logWriter、roles/monitoring.metricWriter、roles/cloudtrace.agent

讀取 Secret Manager 的祕密值需要什麼角色？::roles/secretmanager.secretAccessor

## 🎫 驗證

ADC 的搜尋順序（三個位置）？::① GOOGLE_APPLICATION_CREDENTIALS 環境變數 ② gcloud 使用者憑證 ③ **metadata server（附加的 SA）**

在 Cloud Run / GKE 上需要憑證檔案嗎？::不需要，metadata server 會提供短期 token

Access token 與 ID token 各用來呼叫什麼？::access token → Google Cloud API（GCS/Pub/Sub…）；**ID token → Cloud Run / Cloud Functions / IAP**（aud = 目標 URL）

用 access token 呼叫需驗證的 Cloud Run 會怎樣？::401 Unauthorized

401 與 403 的差別？::401 = 憑證無效/型別錯；403 = 身分正確但缺 IAM 角色

驗證 JWT 的四個必要檢查？::用發行者公鑰驗簽、檢查 iss、檢查 **aud**、檢查 exp/nbf

本機開發要模擬生產 SA 的權限怎麼做？::gcloud auth application-default login --impersonate-service-account=SA（不下載金鑰）

metadata server 取 token 時必須帶什麼 header？::Metadata-Flavor: Google（防 SSRF）

OAuth 2.0 authorization code flow 用在什麼場景？::應用代表**終端使用者**存取他的資源（例如 Google Drive）

「連 Cloud SQL 不要有密碼」怎麼做？需要哪些角色？::IAM 資料庫驗證 + Auth Proxy/Connector（--auto-iam-authn）；需要 roles/cloudsql.client 與 roles/cloudsql.instanceUser

為什麼不能用 IAM 管理 App 的百萬終端使用者？該用什麼？::IAM 是為 GCP 資源存取設計的；終端使用者用 **Identity Platform / Firebase Auth**

## 🗝 祕密與金鑰

Secret Manager 與 Cloud KMS 的分工？::Secret Manager 存**祕密值**；KMS 管**加密金鑰**

`latest` 與釘住版本的取捨？::latest 輪替後自動取新值但行為可能突然改變；釘住版本可重現但輪替後要重新部署

「不重新部署就取得輪替後的新密碼」怎麼配置？::用 volume 掛載 `latest`（env 注入只在啟動時解析）

祕密該在哪裡讀取？放錯會有什麼症狀？::啟動時讀一次或加快取；放在請求路徑上會造成延遲上升與 429

Secret Manager 的 user-managed replication 解決什麼？::資料落地需求（祕密必須留在指定 region）

Google-managed / CMEK / CSEK / EKM 的差別？::Google 管 / 你在 Cloud KMS 管（可輪替撤銷）/ 你自己傳入 / 金鑰在外部 KMS

`FIPS 140-2 Level 3` 對應什麼？::KMS 的 **HSM** 保護等級

什麼是信封加密？為什麼需要？::用隨機 DEK 在本機加密大量資料，只把 DEK 交給 KMS 的 KEK 加密；因為 KMS 的 encrypt API 有大小限制且要減少 API 呼叫

為什麼 KMS admin 不能解密？這叫什麼？::職責分離 —— admin 管金鑰、cryptoKeyEncrypterDecrypter 才能用金鑰

Kubernetes Secret 為什麼不算安全？正解是什麼？::它只是 base64 編碼不是加密；正解是 **Secret Manager + CSI driver**

KMS KeyRing 有什麼不可逆特性？::建立後不可刪除、不可移動

## 🌐 聯邦身分

Workload Identity Federation 的四個步驟？::① 外部工作負載取得自己的 OIDC token ② 用它向 Google STS 交換 ③ pool/provider 驗證信任與條件 ④ 得到短期憑證（或 impersonate SA）

WIF 的 `attribute-condition` 為什麼是必要的？::不設的話任何 repo/工作負載都能換到你的憑證 → 嚴重漏洞

WIF、WIF for GKE、Workforce Identity Federation 的差別？::GCP 外的機器 / GKE 內的 Pod（KSA→GSA）/ 人類使用者（企業 IdP 登入 Console）

GitHub Actions 用 WIF 時 workflow 必須有什麼權限？::permissions: id-token: write（否則拿不到 OIDC token）

WIF 的設定檔可以放進 git 嗎？::可以，它不含祕密（只描述如何交換）

`principal://` 與 `principalSet://` 的差別？::單一身分 vs 符合某屬性的一群身分

## 🚪 存取與應用安全

IAP 解決什麼問題？注入哪些 header？::應用層的存取守門（取代 VPN）；注入 X-Goog-Authenticated-User-Email/-Id 與可驗證的 x-goog-iap-jwt-assertion

為什麼一定要驗證 IAP 的 JWT assertion？::若後端能被繞過，email header 可被偽造 → 必須驗簽 + 檢查 aud，並把後端鎖成只接受 LB 流量

IAP 保護的 Cloud Run 該設什麼 ingress？::--ingress=internal-and-cloud-load-balancing

IAP 與 Identity Platform 的差別？::IAP 管**員工/IAM 身分**的存取；Identity Platform 是你 App 的**終端使用者**身分系統（CIAM）

Identity Platform 的多租戶用在什麼場景？::多租戶 SaaS 的使用者隔離

Web Security Scanner 的風險與正確用法？::它會實際填表單/點按鈕（可能建立刪除資料、寄信）→ 先在 staging 掃或設排除 URL

Security Command Center 的四類來源？::Security Health Analytics（錯誤設定）、Web Security Scanner、Event Threat Detection、Artifact Analysis

「SSH 到沒有公開 IP 的 VM」用什麼？::IAP for TCP forwarding（gcloud compute ssh --tunnel-through-iap）

## 🛂 供應鏈安全

Artifact Analysis 的兩種掃描模式？::on-push 自動掃描 + 持續分析（新 CVE 公布後更新既有映像的漏洞資訊）

映像有大量 CRITICAL CVE，最有效的長期解法？::改用 distroless/minimal 基底映像 + CI pipeline 加掃描 gate（不是手動逐個修）

Binary Authorization 的核心概念四個？::Policy（規則）、Attestor（持公鑰驗證）、Attestation（簽章聲明）、evaluation mode（REQUIRE_ATTESTATION 等）

導入 Binary Authorization 的安全順序？::先 DRYRUN_AUDIT_LOG_ONLY 觀察違規 → 確認後才切 ENFORCED_BLOCK_AND_AUDIT_LOG

為什麼 Binary Authorization 只能用 digest 部署？::tag 可被重新指向（可變），digest 不可變，才能保證驗證的是同一份內容

「不能跳過測試直接部署到生產」怎麼用技術保證？::多階段 attestor（build → qa → security），生產政策要求全部 attestation 齊備

什麼是 provenance（SLSA）？和 Binary Auth 的關係？::可驗證的「這個映像從哪個 commit、用什麼流程建出」紀錄；是 attestation/准入判斷的依據

減少容器攻擊面的四個做法？::multi-stage build、distroless/minimal 基底、非 root 執行、固定基底映像 digest

## 🕸 網路與服務間通訊

Network Policy 與 Cloud Service Mesh 的授權粒度差異？::Network Policy 是 L3/L4（IP + port）；Mesh 是 L7 + 服務身分（可依 HTTP 方法/路徑授權）

Kubernetes 預設的 Pod 間通訊行為？::全部互通 → 需要 Network Policy 才會收斂

加了 egress NetworkPolicy 後 Pod 什麼都連不到，漏了什麼？::沒放行 DNS（kube-system 的 UDP 53）

「服務間加密且不改程式」怎麼做？導入步驟？::Cloud Service Mesh 的自動 mTLS；先 PeerAuthentication PERMISSIVE 過渡再切 STRICT

mTLS 之外還需要什麼才算完整？::AuthorizationPolicy（mTLS 只證明對方是網格成員，不限制他能做什麼）

Cloud Run 之間的安全呼叫需要 Service Mesh 嗎？::不需要 —— 用 IAM run.invoker + ID token
