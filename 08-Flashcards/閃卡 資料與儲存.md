# 閃卡：資料與儲存 #flashcards

> 來源筆記：[[決策樹 資料庫選型]]、[[Cloud Storage]]、[[Firestore]]、[[Spanner]]、[[Bigtable]]、[[一致性 交易與資料複寫]]

---

## 🧭 選型

`global` + `strongly consistent` + `relational` + `99.999%` → 選什麼？::Spanner multi-region

`time-series` / `IoT` / `petabyte` / `single-digit ms` → 選什麼？::Bigtable

`mobile app` + `offline support` + `real-time listeners` → 選什麼？::Firestore（Native mode）

`existing MySQL, minimal changes` → 選什麼？::Cloud SQL

`PostgreSQL 相容` + `更高效能或即時分析（HTAP）` → 選什麼？::AlloyDB

`sub-millisecond` + `session / 排行榜 / 計數器` → 選什麼？::Memorystore（Redis）

`SQL 分析 TB～PB 級資料` → 選什麼？::BigQuery

為什麼不能用 BigQuery 當應用主資料庫？::查詢延遲秒級、有併發限制，不適合 OLTP 的高頻小量讀寫

為什麼低流量工作負載不適合 Bigtable？::Bigtable 最少 1 個節點持續計費，無法縮到 0 → 低流量選 Firestore

## 🪣 Cloud Storage

四種 storage class 的最短儲存期？::Standard 無、Nearline 30 天、Coldline 90 天、Archive 365 天

「資料只需保留 7 天」該用什麼 class？為什麼不是 Archive？::Standard + lifecycle 刪除；Archive 的最短儲存期是 365 天，提早刪仍要付費

Autoclass 解決什麼問題？::存取模式未知或不可預測時，自動在 storage class 間搬移以最佳化成本

signed URL 的三個用途要點？::給沒有 Google 帳號的使用者限時存取特定物件；可用 PUT 讓客戶端直接上傳；需要能簽章的 SA

在 Cloud Run 上產生 signed URL 需要什麼權限？::服務身分需要 iam.serviceAccounts.signBlob（roles/iam.serviceAccountTokenCreator）

「稽核紀錄 7 年任何人都不能刪」該用什麼？::bucket retention policy 設 7 年並 lock（不可逆、不可縮短）

Object Versioning 與 retention policy 的差別？::Versioning 防誤刪（Owner 仍可刪）；retention policy（+lock）是法規級不可變

UBLA（Uniform bucket-level access）做什麼？::停用物件 ACL，一律用 IAM → 最佳實務

大檔案上傳該用什麼？::resumable upload（可中斷續傳）

Cloud Storage 的一致性保證？::強一致（寫入後讀取、列出 bucket 內容都是強一致）

Compose 最多可合併幾個物件？::32

Cloud Storage 的單一物件大小上限？::5 TiB

lifecycle 規則是即時生效的嗎？::不是，大約每天評估一次 → 需要「立即刪除」要用程式/指令

## 📄 Firestore

Firestore 單一文件的大小上限？::1 MiB

Firestore 單一文件的持續寫入速率建議上限？::約 1 次/秒

全站計數器寫入瓶頸的解法？::分片計數器（distributed counter）—— 建 N 個 shard 文件隨機寫，讀取時加總

Firestore batched write / transaction 的操作數上限？::500

Firestore 的查詢效能取決於什麼？::結果集大小，與資料總量無關 → 代價是不能做任意查詢，必須為查詢預先設計結構與索引

Firestore Native mode 與 Datastore mode 的差別？::Native 有客戶端 SDK、即時監聽、離線同步、Security Rules；Datastore mode 只給伺服器端。建立後不能改

Security Rules 與 IAM 分別管什麼？::Security Rules 管客戶端的終端使用者；IAM 管服務帳戶/開發者。伺服器端 SDK 會繞過 Security Rules

Firestore 如何實作「事件只處理一次」？::用 event ID 當文件 ID + create()（已存在會失敗）

Firestore 為什麼不該用 offset 分頁？::沒有真正的 offset（會全掃）→ 用 cursor（startAfter）

Firestore 的 TTL 政策做什麼？::依指定的 timestamp 欄位自動刪除過期文件（省清理程式）

Firestore 的一致性？::強一致

## 🌍 Spanner

Spanner 的「外部一致性」比強一致多保證什麼？靠什麼技術？::交易順序與真實世界時間順序一致；靠 TrueTime（GPS + 原子鐘）

為什麼 `PRIMARY KEY (timestamp)` 是壞設計？三種修法？::單調遞增造成寫入熱點；改用 UUID、雜湊/shard 前綴、或 bit-reverse

Spanner 的 interleaved table 好處與風險？::父子資料實體相鄰 → JOIN 極快；風險是單一父鍵下資料量過大時 split 受限

Spanner 的 stale read 用在什麼場景？::可容忍幾秒舊資料的讀重負載（如儀表板）→ 從最近複本讀、降低對主複本的影響

Spanner 交易回 ABORTED 代表什麼？對程式碼的要求？::交易衝突被中止 → 要能重試，因此交易函式必須可重入（無副作用）

Spanner regional 與 multi-region 的 SLA？::99.99% / 99.999%

什麼是覆蓋索引（Spanner）？::CREATE INDEX ... STORING (欄位) → 查詢不用回主表

## 📈 Bigtable

Bigtable 支援哪三種查詢？::單一 row key 點查、row key 範圍掃描、全表掃描（避免）

Bigtable 有二級索引嗎？::沒有 → 需要時自建「索引表」

`timestamp#deviceId` 與 `deviceId#timestamp` 哪個好？為什麼？::deviceId#timestamp（field promotion）；timestamp 開頭會造成寫入熱點

什麼是 reverse timestamp？解決什麼問題？::Long.MAX_VALUE - epochMillis，讓最新資料排在前面，range scan 不用反向掃

Bigtable 診斷熱點的工具？::Key Visualizer

Bigtable 的 multi-cluster 與 single-cluster App Profile 取捨？::multi-cluster 有 HA 自動切換但不支援單行交易；single-cluster 支援 read-modify-write/CAS

Bigtable 跨叢集複寫的一致性？::最終一致

Bigtable 支援跨 row 交易嗎？::不支援，只有單一 row 的原子操作

## 🗄 Cloud SQL / AlloyDB

Cloud SQL HA（REGIONAL）能抵抗什麼故障？::zone 故障（同 region 跨 zone 同步複寫 + 自動 failover）；不能抵抗 region 故障

Cloud SQL read replica 的一致性？能寫入嗎？::最終一致（非同步）；不能寫入

跨 region 災難復原怎麼做（Cloud SQL）？::跨區 read replica + 手動 promote

Cloud Run 連 Cloud SQL 的四種方式？::Language Connector、Auth Proxy、私有 IP（需進 VPC）、公開 IP + 授權網路（最不推薦）

「不要在程式裡放資料庫密碼」的兩種正解？::IAM 資料庫驗證（用 SA 身分登入）或把密碼放 Secret Manager

Serverless 連線數爆炸的四個修法？::小連線池（2-5）+ 限制 max-instances + read replica 分流 + 加快取（必要時 PgBouncer）

為什麼「讀 replica 再讀自己剛寫的資料」會出錯？::複寫延遲（最終一致）→ read-your-writes 問題。解法是關鍵讀走主庫

AlloyDB 相對 Cloud SQL 的關鍵優勢？::PostgreSQL 相容 + 更高交易效能 + 內建列式引擎（HTAP 即時分析）

## ⚡ Memorystore 與快取

cache-aside 的三個步驟？::先查快取 → miss 就查來源 → 回寫快取（設 TTL）

快取穿透、雪崩、擊穿的解法？::穿透→快取空值+Bloom filter；雪崩→TTL 加隨機抖動；擊穿→互斥鎖/single-flight

Memorystore Basic 與 Standard tier 的差別？::Basic 單節點無複本無自動 failover；Standard 主從跨 zone + 自動 failover

Cloud Run 連 Memorystore 需要什麼？::Direct VPC egress 或 Serverless VPC Access（Memorystore 只有私有 IP）

更新資料時先刪快取還是先更新 DB？::先更新 DB，再讓快取失效（cache-aside + invalidate）

什麼時候該用 Cloud CDN 而不是 Memorystore？::靜態內容要在邊緣快取給全球使用者時

## 📊 BigQuery

把應用事件送進 BigQuery 的四種方式？::Storage Write API（串流推薦）、舊 insertAll、批次載入（GCS，免費）、Pub/Sub BigQuery 訂閱（免程式碼）

為什麼 `SELECT * ... LIMIT 10` 不省錢？::BigQuery 是列式儲存，掃描所有選到的欄位；LIMIT 不減少掃描量。要看資料用 bq head / preview（免費）

BigQuery 省錢的四個做法？::不要 SELECT *、分區（partition）、叢集（cluster）、require_partition_filter / maximum bytes billed

「分析師不能看到 email 欄位」與「只能看自己部門的列」分別用什麼？::column-level security（policy tag）/ row-level security（或 authorized view）

---

## 🔄 一致性

最終一致、強一致、外部一致各舉一例？::最終一致=Cloud SQL read replica / Bigtable 跨叢集；強一致=Firestore / Cloud Storage；外部一致=Spanner

RTO 與 RPO 的差別？::RTO=恢復所需時間；RPO=可接受的資料遺失量（同步複寫 RPO=0）

「資料存進 DB 就一定要發出事件」該用什麼模式？::transactional outbox（同一交易寫業務資料與 outbox 表，背景程序再 publish）

跨服務的原子性怎麼做？::沒有 2PC → 用 Saga + 補償交易 + 冪等（Workflows 的 except 步驟）

Cloud Storage 怎麼做樂觀鎖？::上傳時帶 ifGenerationMatch（不符會回 412）
